# AI Study Assistant — Backend (المرحلة 1-8: كل الميزات الأساسية + جاهزية إنتاج مُتحقَّق منها)

Backend فعلي وقابل للتشغيل مبني بـ **FastAPI**، يطبّق دورة MVP كاملة (§33):
تسجيل حساب → دخول → رفع ملف → استخراج نصه (نصيًا أو عبر OCR) وتقسيمه →
تلخيص/محادثة عبره → توليد اختبار وبطاقات تعليمية بالذكاء الاصطناعي وحفظ
نتائجها → تجميع إحصائيات تقدّم حقيقية (بما فيها وقت دراسة فعلي).

الاختبارات ضدها — وليس فقط "من المفترض أن يعمل".

## 🪟 إصلاح Windows: خطأ ترميز عند بدء التشغيل (تحديث جديد)

إذا واجهت `UnicodeDecodeError: 'charmap' codec can't decode byte...` عند
تشغيل `uvicorn app.main:app --reload` على Windows: هذا كان خطأ حقيقيًا
اكتُشف فعليًا — `alembic.ini` كان يحتوي تعليقًا بالعربية، وWindows يفتح
ملفات `.ini` بترميز النظام الافتراضي (غالبًا `cp1252`) بدل UTF-8، فيفشل
عند أي حرف غير ASCII. **تم إصلاحه**: `alembic.ini` أصبح ASCII خالصًا
بالكامل (تحقّقنا من ذلك حرفيًا بمحاكاة قراءته بـ`cp1252`)، و`.env`
أصبح يُقرأ بـ`utf-8` صراحةً (`env_file_encoding` في `config.py`) كإجراء
احترازي إضافي. أي ملف `.ini`/إعداد آخر يُضاف مستقبلًا لهذا المشروع يجب أن
يبقى ASCII خالصًا لنفس السبب — التعليقات التوضيحية بالعربية تذهب لملفات
`.py` أو `.md` فقط (تُقرأ بـUTF-8 دائمًا بغض النظر عن نظام التشغيل).

## 🔐 Google Sign-In حقيقي (تحديث جديد)

`POST /api/auth/google` يقبل ID Token من Flutter، يتحقق منه **فعليًا مع
خوادم Google** (توقيع رقمي حقيقي، وليس فك تشفير محلي)، ثم:
- ينشئ حسابًا جديدًا تلقائيًا إن كانت أول مرة
- يسجّل الدخول لنفس الحساب في المرات التالية (بدون تكرار)
- **يربط تلقائيًا** بحساب بريد/كلمة مرور موجود مسبقًا بنفس البريد الإلكتروني
  (بدل إنشاء حساب مكرَّر)، مع بقاء تسجيل الدخول بكلمة المرور القديمة يعمل

**تم اختباره فعليًا بـ7 سيناريوهات** بتزييف تحقق Google (`test_google_auth.py`)
— بما فيها الحالة الحسّاسة: مستخدم Google الخالص (بلا كلمة مرور إطلاقًا)
يحاول تسجيل الدخول بكلمة مرور فيُرفَض بـ401 نظيف بدل انهيار داخلي (كان
هذا bug حقيقي محتمل بسبب جعل `hashed_password` قابلة لـ NULL — أُصلح
بالتحقق الصريح قبل استدعاء `verify_password`).

**تم اكتشاف وإصلاح خطأ Migration حقيقي أثناء هذا العمل**: SQLite لا يدعم
`ALTER COLUMN ... DROP NOT NULL` (خلافًا لـ PostgreSQL الذي يدعمه بلا
مشاكل) — الحل: `batch_alter_table` بدل `alter_column` المباشر، يعمل على
قاعدتي البيانات معًا. تم التحقق من upgrade/downgrade فعليًا على كليهما.

**ما يحتاج إعدادك أنت (لا يمكن تجاوزه):**
1. أنشئ مشروع Google Cloud (أو استخدم نفس مشروع Gemini)
2. من https://console.cloud.google.com/apis/credentials أنشئ **Web OAuth
   Client ID**، وضع قيمته في `.env` كـ `GOOGLE_CLIENT_ID=...`
3. لـ Android: أنشئ أيضًا Android OAuth Client ID (يحتاج SHA-1 fingerprint
   + application ID)، وفي Flutter ضع نفس الـ Web Client ID في
   `lib/core/network/google_auth_config.dart` كـ `serverClientId`
4. **هذا الجزء تحديدًا لم يُختبَر فعليًا من طرفي** — لا أملك بيانات اعتماد
   Google Cloud حقيقية. اختبرت فقط منطق الخادم بعد وصول رمز صالح (بتزييف
   التحقق)، وليس مسار OAuth الكامل من الجهاز إلى Google وعودةً.

```bash
python test_google_auth.py
```

## 🏭 جاهزية الإنتاج — تفاصيل ما تم اختباره فعليًا

### ⚠️ عند النشر على Render/Railway: ثبّت إصدار Python صراحةً

اكتُشف فعليًا: منصات الاستضافة قد تستخدم أحدث إصدار Python متاح تلقائيًا
(مثل 3.14 الصادر حديثًا)، بينما `psycopg2-binary` (وحزم أخرى تعتمد على
امتدادات C) قد لا تملك بعد نسخة ثنائية متوافقة معه، فيفشل النشر بخطأ
`ImportError: undefined symbol: _PyInterpreterState_Get`. ملف
`runtime.txt` في جذر المشروع (يحتوي `3.12.7`) يُجبر Render على استخدام
هذا الإصدار المستقر بدل الأحدث تلقائيًا — نفس الإصدار المُختبَر محليًا
طوال هذا المشروع. إن كنت تنشر على منصة أخرى، ابحث عن طريقتها لتثبيت
إصدار Python (عادة متغير بيئة `PYTHON_VERSION`).


### PostgreSQL
```bash
# في .env:
DATABASE_URL=postgresql://user:password@localhost:5432/ai_study_db
```
يحتاج `psycopg2-binary` (موجود أصلًا في `requirements.txt`). **تم تشغيل
كامل حزمة الاختبارات (73/73) ضد PostgreSQL 16 فعليًا** في بيئة الاختبار،
وليس افتراضًا لأن "SQLAlchemy يدعم كلاهما نظريًا".

### Alembic Migrations — تُطبَّق تلقائيًا الآن عند بدء التشغيل

**تحديث مهم**: `app/main.py` يُطبّق `alembic upgrade head` تلقائيًا في كل
مرة يبدأ فيها التطبيق — لم يعد `create_all` مُستخدَمًا إطلاقًا. هذا يحل
مشكلة شائعة كانت تحدث سابقًا: تعديل نموذج (مثل إضافة `google_id`) ثم
الحصول على `no such column` عند التشغيل، لأن `create_all` **لا يُحدّث
جداول موجودة مسبقًا** — ينشئ الجداول المفقودة فقط.

**الأهم**: هذا يعمل تلقائيًا حتى مع قاعدة بيانات **قديمة** كانت أُنشئت
سابقًا عبر `create_all` (قبل اعتماد Alembic في هذا المشروع) — الكود
يكتشف هذه الحالة تحديدًا (وجود جدول `users` بلا جدول `alembic_version`)
ويُعلِّم (`stamp`) القاعدة عند أول Migration تلقائيًا بدل محاولة إعادة
إنشاء جداول موجودة أصلًا (وهذا كان سيفشل بخطأ "table already exists").
**تم اختبار هذا فعليًا بمحاكاة قاعدة بيانات قديمة حقيقية فيها بيانات،
والتأكد أن لا شيء يُفقَد وأن العمود الجديد يُضاف بشكل صحيح.**

عند تعديل أي نموذج مستقبلًا:
```bash
alembic revision --autogenerate -m "وصف التغيير"
```
ثم شغّل التطبيق عاديًا (`uvicorn app.main:app --reload`) — الترحيل
يُطبَّق تلقائيًا، بلا أي خطوة يدوية إضافية وبلا حذف أي قاعدة بيانات أبدًا.

أوامر يدوية إضافية عند الحاجة:
```bash
alembic upgrade head      # تطبيق يدوي (نادرًا ما تحتاجه، يحدث تلقائيًا)
alembic downgrade base    # للتراجع الكامل (اختبرناه فعليًا أيضًا)
```
`migrations/env.py` يقرأ `DATABASE_URL` من نفس `.env` الذي يستخدمه
التطبيق تلقائيًا — لا إعداد مزدوج. **تم اختبار upgrade وdowngrade فعليًا
على PostgreSQL وSQLite معًا.**

### OCR للملفات الممسوحة ضوئيًا (§7)
يحتاج تثبيت نظامي (خارج pip):
```bash
# Ubuntu/Debian:
sudo apt-get install tesseract-ocr tesseract-ocr-ara poppler-utils
# macOS:
brew install tesseract tesseract-lang poppler
```
`pytesseract` و`pdf2image` و`Pillow` موجودة أصلًا في `requirements.txt`.
**تم التحقق فعليًا**: أُنشئ ملف PDF حقيقي يحتوي صورة فقط (بلا أي طبقة نص
— تأكّدنا أن `pypdf` العادي يُعيد نصًا فارغًا منه)، ثم رُفع عبر الـ API
الفعلي، واستخرج Tesseract النص المكتوب في الصورة **بدقة 100%** وحفظه
كمقاطع (Chunks) صالحة للاستخدام في RAG.

قيود معروفة:
- بلا Tesseract مثبَّتًا نظاميًا، يتراجع الكود بأمان (لا نص لتلك الصفحة،
  دون تعطّل الرفع بالكامل) — لأن `pytesseract` يستدعي برنامج tesseract
  الخارجي، وليس مكتبة Python خالصة.
- حد أقصى 30 صفحة OCR لكل ملف (`MAX_OCR_PAGES` في `text_extraction.py`)
  لتفادي تعليق الطلب طويلاً على ملف كامل ممسوح ضوئيًا وضخم.
- لم تُختبَر دقة OCR على نص عربي حقيقي بخط يدوي أو جودة مسح رديئة — فقط
  نص إنجليزي مطبوع واضح. النموذج (`lang="ara+eng"`) يدعم العربية نظريًا.

## ❌ لم يُنفَّذ بعد

- pgvector الفعلي (حاليًا embedding مخزَّن كنص JSON، يعمل بشكل صحيح على
  نطاق صغير لكن بدون تسريع فهرسة Vector حقيقي)
- **دقة OCR على نص عربي حقيقي غير مُختبَرة** (فقط نص إنجليزي مطبوع واضح)
- **مسار Google OAuth الفعلي من الجهاز غير مُختبَر** — فقط منطق الخادم بعد
  وصول رمز صالح (راجع القسم أعلاه للتفاصيل الكاملة)
- Admin Dashboard (§34)، نظام الاشتراكات (§35) — خارج نطاق الأولوية الحالية

## الخطوة التالية المقترحة

1. جرّب `summary`, `questions`, `flashcards` فعليًا من التطبيق (وليس `chat`
   فقط) — آخر جزء من AI غير مُتحقَّق منه بنفس الثقة
2. إذا كنت تخطّط للنشر الفعلي: بدّل `DATABASE_URL` لـ PostgreSQL، شغّل
   `alembic upgrade head`، واضبط `REDIS_URL` — الثلاثة مُختبَرة وجاهزة
3. جرّب رفع PDF ممسوح ضوئيًا حقيقي (وليس نص/صورة تجريبية) من جهازك للتأكد
   من جودة OCR على محتوى واقعي
4. أعدّ Google Cloud Console فعليًا (Web + Android OAuth Client IDs) وجرّب
   "المتابعة عبر Google" من التطبيق الحقيقي — هذا المسار الوحيد المتبقّي
   غير المُختبَر بالكامل في نظام المصادقة
